# CryptoAudit benchmark corpus

The corpus is split **by role**, so the information boundary is a directory boundary.
Every role mirrors the same `<rule>/<case_id>/` structure:

```
benchmark/
├── cases/<rule>/<case_id>/       PUBLIC   module.py + case.yaml
├── expected/<rule>/<case_id>/    HIDDEN   oracle.yaml + V1/V2/V3 check files
├── artifacts/<rule>/<case_id>/   HIDDEN   legacy data persisted by the original code (V3)
└── results/                      LOCAL    run outputs and exports (git-ignored)
```

| Path | Visible to | Contents |
|---|---|---|
| `cases/…/module.py` | Analyzer, Context Engine, Repair Engine (S1–S4) | The vulnerable program |
| `cases/…/case.yaml` | Repair Engine | Case id, rule id, target Python version, allowed libraries |
| `expected/…/oracle.yaml` | Validation only | Which check files back V1/V2/V3, V3 applicability and gating |
| `expected/…/v1_functional.py` | Validation only | Functional behaviour checks (V1) |
| `expected/…/v2_security.py` | Validation only | Executable cryptographic security-property checks (V2) |
| `expected/…/v3_compatibility.py` | Validation only | Legacy artifact compatibility checks (V3; CR1–CR4) |
| `artifacts/…/*.json` | Validation only | Data persisted by the original implementation |

Rules:

- Repair strategies receive a `PublicCase` from `cryptoaudit.ingest.benchmark_loader`, which only
  reads `cases/`.
- `cryptoaudit.validation.oracle` is the only loader for `expected/` and `artifacts/`; an
  import-boundary test keeps the generation side (`repair`, `context`, `llm`, `ingest`, `analysis`,
  `rules`) from importing `validation`.
- Every hidden file contains a `CANARY: cryptoaudit-hidden-oracle-<case_id>` marker. Leakage tests
  assert no canary ever appears in a repair request or prompt.
- Legacy artifacts are generated by running the original `cases/…/module.py`, so they are exactly
  what the vulnerable implementation persisted.

## Check file format

Check files define `check_*(ctx)` functions. They run inside the validation sandbox through
`cryptoaudit.validation.sandbox.harness` and use:

- `ctx.load_candidate()` — import a fresh copy of the candidate module
- `ctx.load_json(name)` / `ctx.artifact(name)` — read files from the case's `artifacts/` directory

An `AssertionError` is a FAIL; any other exception raised by the candidate is also a FAIL.
A check file that cannot load is a validator ERROR.

## Adding a case

1. Add `cases/<rule>/<case_id>/module.py` that the CryptoAudit Analyzer flags for `<rule>`.
2. Add `cases/<rule>/<case_id>/case.yaml` (no hidden information in it).
3. Add `expected/<rule>/<case_id>/` checks and, for V3, `artifacts/<rule>/<case_id>/` produced by
   running the original module.
4. Run `pytest tests/integration/test_validation_pipeline.py`: the original must pass V1 (and V3)
   and fail V2; the reference repair in `tests/fixtures/reference_repairs/` must pass all gates.
